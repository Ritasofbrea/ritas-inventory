# Rita's Italian Ice – Brea Inventory & Tasks App

## 1. What this is
A mobile-first PWA for Rita's Italian Ice, Brea location — Rita's is the franchise brand, not a person. Inventory counting/ordering **plus** a full daily task/checklist system, sticky notes, and weekly flavor planning. Owners (`owner` role): Josh and Gina; shift leads and staff use it on a shared ViewSonic touchscreen mounted in the store, plus personal phones. Installable via "Add to Home Screen" (standalone, no browser chrome).

Auto-reload: every deploy bakes a build id (`VERCEL_GIT_COMMIT_SHA`, see `next.config.ts`) into the bundle. `AutoReloadWatcher` (mounted in root layout) polls `/api/version` every 5 min (3s while idle) and does a hard reload when the server's build id no longer matches the page's — silent, no banner. A `localStorage` loop-guard (`ritas_autoreload_log`) blocks repeat reloads within 10 minutes. Disable via server env var `AUTO_RELOAD_DISABLED=1` (needs a redeploy to take effect — see §3).

This directory (`ritas-app/`) IS the Next.js root and the git repo root.

## 2. Commands
- `npm install` — install deps
- `npm run dev` — `next dev` (Turbopack)
- `npx tsc --noEmit` — typecheck (there is **no** `npm run typecheck` script)
- `npm run lint` — `eslint .`
- `npm run build` — `next build`

A small persisted regression suite lives in `tests/e2e/` — see `tests/e2e/README.md` for full setup/run instructions. It covers patch 29's role checks, patch 28's step-completion gating, and the Home/Switch logout race, over `npm run dev` on localhost (never a Vercel preview — SSO-protected; see §6):
```
npm run test:e2e                 # all four suites
npm run test:e2e:role-checks     # patch 29: requireRole 401 vs 403 across route-access.md's tiers
npm run test:e2e:step-checks     # patch 28: can't complete a checklist-style task with unchecked steps
npm run test:e2e:logout-race     # Home/Switch tap survives a failed/hung POST /api/logout
npm run test:e2e:row-cap-checks  # patch 41: last-per-item/velocity/par-suggestions don't depend on a bulk fetch PostgREST's 1000-row cap could truncate
npm run test:e2e:cleanup         # sweep any leftover ZZTEST fixtures
```
`role-checks`/`step-checks` never use a PIN — they log in as two dedicated accounts, `ZZTEST Owner`/`ZZTEST Shift Lead`, created by `supabase/e2e-test-accounts.sql` and kept permanently `active = true` by `supabase/zztest-accounts-permanent.sql` (both idempotent; run once each, Josh runs all SQL per §6). `helpers/auth.mjs` mints a real, production-signed session cookie for each directly via `createSessionToken` (`src/lib/session-token.ts` — the pure signing logic split out of `src/lib/session.ts` so it has no Next.js import and can be called from a plain Node script), instead of calling `/api/pins/verify`. The two account names are hardcoded literals in that file, not parameters. No toggling before/after a run anymore: `ZZTEST Owner` is invisible everywhere the app queries owners (those lists are hardcoded by name, never DB-driven by `active`); `ZZTEST Shift Lead` is explicitly filtered out of the three real call sites that list active shift leads for production behavior — see §8. Both accounts' `pin` column is set to a long non-digit value, which `/api/pins/verify` now rejects before any DB lookup (real PINs are always 4-6 digits), so neither account can ever be logged into through the normal PIN screen. `logout-race` needs no PINs at all, just `npx playwright install chromium` once. This is **not** full coverage — it's three specific regressions, not route-access.md's whole table. For anything beyond these three, the older convention still applies: write a throwaway script with `ZZTEST`-prefixed fixtures, seed/clean up via direct Supabase REST calls using the service-role key (read from `process.env`, never printed/logged — `tests/e2e/helpers/rest.mjs` is a ready-made example), and remember hard-deleting a template **detaches** (doesn't delete) its done/missed instances, so a template-first cleanup sweep misses them — also sweep `task_instances` directly by title/`checklist_name`. Playwright's `getByRole`/text matchers are case-insensitive **substring** by default — pass `exact: true` or you'll get accidental matches (e.g. "Delete list" matching inside a fixture named "...Delete List").

## 3. Architecture map
- **Session & roles** — `src/lib/session.ts`. HMAC-SHA256-signed cookie `ritas_session` (httpOnly, `sameSite: lax`, `Secure` only when `NODE_ENV=production` so local http testing works). Roles: `owner` / `shift_lead` / `staff`. `getSession`/`requireRole` also revoke a structurally-valid cookie if the named person is `active=false` or if `owners.updated_at`/`shift_leads.updated_at` is newer than the cookie's `iat` (PIN change or deactivation kills existing sessions immediately, no 30-day wait). Staff sessions name no one and can't be revoked this way. `SessionGuard` (mounted globally) patches `window.fetch` so **any** 401 anywhere bounces the device to `/login`.
- **PIN verify** — `src/app/api/pins/verify/route.ts`. Checks the submitted PIN against `owners.pin` or `shift_leads.pin` directly (plaintext, see §5), rate-limited via `src/lib/rate-limit.ts` (`login_attempts` table: blocks after 10 failures from one IP in 15 minutes; purged after 7 days by the nightly cron). On match, sets the session cookie.
- **Tasks: templates/instances/generator/cron** — `src/lib/task-server.ts` is the core server logic (`generateInstancesForDate`, `sweepMissedInstances`, `createChecklist`, `renameChecklistList`, `deleteChecklistList`, `moveChecklistList`, `addChecklistItem`, `moveChecklistItem`, `moveTemplateToSection`, `renameChecklistSection`, `deleteTemplate`/`deleteOneOffTask`, step functions — see below). `/api/cron/generate-tasks` runs daily via Vercel Cron (`vercel.json`), auth'd by `Authorization: Bearer $CRON_SECRET` which Vercel sends automatically when that env var is set; fails closed with no secret configured. `/api/cron/cleanup-photos` runs nightly: purges task/note photos older than 90 days and `login_attempts` rows older than 7 days.
- **`src/lib/tasks.ts`** — shared grouping/ordering/date helpers: `buildChecklistGroups`/`buildTemplateChecklistGroups` (group by `checklist_name`→`section`), `sortChecklistNames`, `sortStandalone`, `groupHistoryByDay`, `todayInTZ`/`addDays`/`toHM`/`formatDueTime`/`isOverdue`/`normalizeListName`.
- **Steps + step checks** — a template can be `step_style: 'none' | 'reference' | 'checklist'`. `'checklist'` templates carry ordered sub-steps (`task_template_steps`); an instance can't be marked done until every step is checked (`task_instance_step_checks`, enforced in `canCompleteInstance`). `attachStepsToInstances` hydrates steps onto instances live from the template (not snapshotted — a template's steps mid-day change what an already-generated instance shows). `checkStep`/`uncheckStep` upsert/delete a `task_instance_step_checks` row on `(instance_id, step_id)` with `checked_by` always `null` — anonymous by design, no name required or stored.
- **Checklists/lists** — `checklists` table (`name` PK, `due_time`, `active`, `sort_order`). Owner-only CRUD via `/api/checklists`. Creating sets `sort_order = max+1`. Renaming cascades to templates and to open (and same-day done) instances in one operation; already-completed instances from before a rename keep the old name, so they show under a separate old-name card on Today's view until they roll into History — intentional, not a bug. Turning a list `active=false` stops the generator from making new instances for its templates and hides its open instances from the To-Do tab/counts/notifications for everyone; turning it back on resumes. Hard-deleting a list cascades to its templates using the same per-template rule as a single task's hard delete (open instances deleted, done/missed instances detached via `template_id=null`, so History stays intact).
- **Notes** — `src/lib/notes.ts` (types/helpers) + `notes-server.ts`. Tables: `notes`, `note_replies`, `note_acknowledgments`, `note_photos` (up to 3 per note). Delete = archive (`archived`/`archived_at`), not destroy. `owner_only` notes are private to the owner role with no exceptions (an earlier per-device "known author" exception leaked private notes and was removed). `requires_ack` notes track who acknowledged in `note_acknowledgments`; `computeAckDenominator` (`src/lib/staffColor.ts`) computes how many people are required to ack (every active staff + shift lead, deduped, minus owners, minus a shift-lead author's own note).
- **Flavors** — `src/lib/flavors.ts`. `FLAVOR_SECTIONS` defines three spaced-out slot "lanes" so growing one never renumbers another: `ice` (slots 1–12: italian_ice/cream_ice/sugar_free), `soft_serve` (101–103), `hs_custard` (201–212). Tables `flavors`/`flavor_weeks`/`flavor_week_slots`; a slot snapshots `flavor_name`+`flavor_type` at pick time so a past week's display survives the catalog entry being deleted later.
- **Shared components** — `src/components/`: `Navigation`, `SessionGuard`, `AutoReloadWatcher`, `StaffName`, `BackToTop`, `ScrollToSaveButton`, `PinModal`/`PinManagementView`. `src/components/todo/`: `TimeField` (custom hour/minute/AM-PM `<select>`s — see §7), `TemplatesView`, `ManageListModal`, `ShiftLeadView`/`StaffView`, `NotesBoard`/`AddNoteModal`/`AckModal`, `FlavorSlotPicker`/`FlavorCatalogView`, `HistoryView`/`MissedView`, `ConfirmModal`.
- **Inventory pages** — `/count`, `/order-list`, `/receive-order`, `/history`, `/reports`, `/par-settings`, `/manage-items`, `/dashboard`, `/current-stock`, `/adjust` (Correct Count). Tables `items`, `inventory_counts`, `order_history`/`order_history_items` (snapshots `item_name` at order time). Originally the base system predating tasks/notes/flavors; since extended with seasonal on/off, storage stock, a flavor program badge, vendor order schedules/reminders, and patch 55's Ice Mix box ordering — see the bullets below and §9.
- **Vendor order schedules & reminders** (patch 44) — `src/lib/vendor-schedule.ts`: `vendorKeyForItem` (the one shared "which vendor bucket does this item belong to" check — a literal `'other'` distributor and no distributor both fold to `'other'`; every grouping site uses this, not its own copy, after patch 46 fixed a double-display bug from three disagreeing copies), `computeVendorDueInfo`/due-tag logic, DST-safe Pacific-time day math (via `tasks.ts`'s Pacific helpers). `src/lib/order-list-server.ts` pages `order_history` (immune to the 1000-row cap) to compute per-vendor "needs ordering" counts for the cron and `/api/vendor-schedules`. `src/lib/vendor-reminder-server.ts` drives the GitHub-Actions-cron-hit reminder route, deduped by `vendor_reminder_log` (writes the dedup record before pushing, not after, so a failed log write skips that tick's push instead of risking a double-send). Per-vendor "Order Placed"/"Nothing to order"/"Undo" write `vendor_week_status` (current state, upsert/delete) and best-effort `vendor_week_status_log` (append-only audit trail).
- **Order quantity/case-unit helpers** — `src/lib/order-units.ts`: `usesBoxOrdering`/`getOrderUnitLabel`/`getDefaultOrderQty`/`packSizePreview` (case/box wording and default order-quantity math off `items.pack_size`) and `formatGallonsWithBoxes` (patch 55's box+gallon breakdown for Ice Mix). `items.pack_size` only ever changes through owner-only `PATCH /api/items/pack-size`.
- **Storage write safety** — `src/lib/storage-server.ts`'s shared `withRetry` compare-and-swap wrapper backs `applyStorageChange`/`applyStorageCorrection` (patch 38/39) and `applyCurrentCountIncrement`/`applyRawCountDelta` (patch 48, the non-storage receive path) — one retry-on-conflict primitive for every write where two concurrent requests (owner on phone, shift lead on the touchscreen) could otherwise race and lose an increment. A multi-item receive applies sequentially and rolls back every item already applied in the same receipt if one item's write can't be applied after retries are exhausted.
- **Photo uploads** — `src/lib/photo.ts` translates Supabase Storage's raw upload-rejection messages (size/mime-type) into plain language; both `note-photos` and `task-photos` buckets enforce a 5MB cap + an allowed-image-types list. Note photos upload under an unguessable `crypto.randomUUID()`-prefixed path. `src/lib/note-photo-cleanup-server.ts` sweeps orphaned (never-attached) files in the `note-photos` bucket nightly — dry-run only unless `NOTE_PHOTO_CLEANUP_ENABLE_DELETE=1` is explicitly set, and never deletes anything if its `note_photos` lookup errors or comes back unexpectedly empty.
- **Backups** — `scripts/backup.mjs` (read-only, pages all 30 public tables + lists both storage buckets, verifies row counts, atomic rename, keeps the 8 newest) + `scripts/backup-check.mjs` (`npm run backup:check`), run by two launchd LaunchAgents (`scripts/*.plist` + `install-backup-jobs.sh`) — weekly to iCloud Drive, plus a daily staleness check. See `scripts/BACKUP-README.md`: the backup contains plaintext PINs and push subscription keys.
- **Version/auto-reload plumbing** — `next.config.ts` bakes `NEXT_PUBLIC_BUILD_ID`; `/api/version` (`force-dynamic`, no auth — must never 401) returns the live build id + `autoReload` boolean read fresh from `AUTO_RELOAD_DISABLED` on every request.

## 4. Database
Every table has Row Level Security **enabled with no policies** (`supabase/enable-rls-all.sql`) — the anon key (public, embedded in the client bundle) is locked out of all of them. The app only ever uses the service-role key (`getServerSupabase()` in `src/lib/supabase.ts`), server-side only, which bypasses RLS entirely. **Never** request or print `SUPABASE_SERVICE_ROLE_KEY`'s value.

Key tables (not exhaustive — see `supabase/*.sql` for full history):
- `items`, `inventory_counts`, `order_history`/`order_history_items` — base inventory (pre-dates tasks). `items` has since grown: `is_off` (patch 37, seasonal on/off, owner-only via `/api/items/off`), `has_storage`/`storage_count`/`storage_updated_at` (patch 38, owner-only via `/api/items/storage*`, backed by `storage_moves` history + patch 48's shared retry-on-conflict writer), `pack_size` (patch 44, owner-only via `/api/items/pack-size` — "how many MAIN-unit units = 1 order case/box," independent of `units_per_sub_unit`, never participates in stock math), `flavor_id` (patch 45, nullable FK → `flavors(id)`, owner-only via `/api/items/flavor`, read live via a join on every `GET /api/items`, never snapshotted). `order_history` gained `note_review_needed`/`note_reviewed_by`/`note_reviewed_at` (patch 44, a receipt-note review flag — deliberately its own column rather than reusing `resolved`, which already means something else on short-shipment rows); `order_history.vendor` (patch 58, nullable text, the `vendorKeyForItem` key) is set on new `ordered` rows only; older orders and all receipt rows stay null. `order_history.related_order_id`'s FK is `ON DELETE SET NULL` (patch 50, brought the live constraint back in line with the documented design after it was found enforcing a blocking FK instead).
- `storage_moves` (patch 38/39) — history of every storage⇄store/add/correction change, optimistic-concurrency guarded.
- `vendor_schedules`, `vendor_week_status`, `vendor_week_status_log`, `vendor_reminder_log` (patch 44) — vendor due-day config, per-week ordered/skipped state (current value + append-only audit trail), and reminder dedup log. `owners.order_alerts_enabled`/`receipt_note_alerts_enabled` and `push_subscriptions.owner_name` (patch 44) gate/attribute per-owner push reminders.
- `owners` (`name` PK, `pin`, `active`, `created_at`, `updated_at`), `shift_leads` (`id` PK, `name` unique, `pin`, `active`, `created_at`, `updated_at`) — real per-person PINs, **plaintext**. A legacy generic `pins` table (`name` PK `'owner'/'shift_lead'`, `value`) predates these; both its rows were deleted when `owners`/`shift_leads` were introduced and no app code references it anymore (verified by grep) — it's vestigial but was never dropped.
- `staff` (`name` unique, `active`, `color`) — `created_by`/`assigned_to` on tasks use a separate short-name convention (`Josh`/`Gina`/`Valerie`), reconciled to staff full names via alias maps in `staffColor.ts`, not a FK.
- `checklists`, `task_templates`, `task_instances`, `task_template_steps`, `task_instance_step_checks` — see §3. **`checklist_name`/`section` on `task_templates`/`task_instances` are plain free-text columns, NOT a foreign key to `checklists.name`** (confirmed: no such `references` anywhere in `supabase/`). `task_instances` **snapshot** `checklist_name`/`section`/`sort_order`/`title`/etc. from their template at generation time — not a live join — so a rename/reorder must explicitly push onto already-generated instances or it won't show until tomorrow's regeneration. `task_instances.template_id → task_templates(id)` has **no cascade**; hard-deleting a template requires explicitly handling its instances (exactly what `deleteTemplate`/`deleteChecklistList` do).
- `notes`, `note_replies`, `note_acknowledgments`, `note_photos` — see §3.
- `flavors`, `flavor_weeks`, `flavor_week_slots` — see §3.
- `clover_items`, `clover_item_mappings` — Clover POS menu-item → inventory-item consumption mapping (seeded, not actively built out further).
- `count_draft`, `push_subscriptions`, `login_attempts` — single-row shared count-entry draft, web push subscriptions, login rate-limit log.

## 5. Security model
- Session cookie is HMAC-signed and verified with `timingSafeEqual`; expiry + role + revocation checked server-side on every `requireRole` call (see §3). **401** = no/invalid/expired/revoked session. **403** = valid session, wrong role for this route.
- Rate limiting: 10 failed PIN attempts from one IP in 15 minutes blocks further attempts with 429 (doesn't even check the PIN); the log purges after 7 days.
- Owner-only routes (server-enforced, not just hidden in the UI): list create/rename/move/activate/delete, template/list hard delete, task-template create/edit for most fields.
- **PINs are plaintext** in `owners.pin`/`shift_leads.pin` — verified directly in `/api/pins/verify/route.ts`, which does `.eq('pin', pin)`. Until hashing ships, they're protected only by RLS (see §4) locking the anon key out — only the server, via the service-role key, can ever read `owners.pin`/`shift_leads.pin`.
- **PIN hashing is patch 31 — planned and paused, not started.** A prompt/spec for it already exists; no code or branch does. Verified with `git branch -a`: only `main` and `patch-29-sessions` exist, and no commit anywhere mentions hashing PINs. If a future session is told a `patch-31-pin-hash` branch exists, re-verify with `git branch -a` before trusting it — don't repeat an unverified claim about code existing just because the patch itself is real and queued.

## 7. Design rules
- Never reuse an existing color's/badge's/icon's/border's established meaning for something new — invent a new badge/icon/border instead of overloading one that already means something else.
- New tags/labels default to a neutral gray outlined badge (not a solid color), so they never collide with an existing status color's meaning (see patch 40/43 for shipped examples).
- Custom `TimeField` only, never a native `<input type="time">` — Safari/WebKit renders an empty native time input with a misleading phantom time instead of truly blank.
- Prefer deactivate/archive over hard delete; when something is deleted/renamed, snapshot the name/value it had so history displays correctly after the source changes or disappears.
- Big touch targets everywhere (shared touchscreen device) — buttons are `min-h-[48px]` or larger.
- No hover-only affordances/behavior.
- To-Do tab: no PIN and no name/staff picker required for anything **except** picking a name when completing a main (non-step) task.
- Dashboard must not duplicate Order List's content.

## 8. Gotchas
- **Switch/Home logout race**: a deliberate Home/Switch tap (`Navigation.tsx`) calls `POST /api/logout` then navigates to `/login`; if that call fails/times out, the session cookie may still look valid when `/login` runs its own "returning staff device" auto-skip check, making a deliberate exit look like it did nothing. Fixed via `SKIP_LOGIN_AUTOSKIP_KEY` in `sessionStorage` (`SessionGuard.tsx`), set right before navigating, which tells `/login` to skip that one check.
- **Instance snapshot staleness**: because `task_instances` snapshot template fields at generation time (not a live join), renaming/reordering/moving a template requires an explicit sync onto already-generated open (and same-day done) instances, or the change won't show until the next day's cron regeneration.
- Next.js's built-in dev-tools indicator badge only appears under `next dev` — it's not present in any real deploy (`next build`/Vercel Preview/Production), so don't mistake its absence for a bug.
- A Vercel environment variable marked "Sensitive" can be written but never read back (via dashboard or API) once saved — if you need to confirm a value, ask Josh to check it directly rather than trying to fetch it.
- Running `rm -rf .next` while `next dev` is still running crashes the dev server (MODULE_NOT_FOUND/ENOENT) — kill it first, then restart cleanly.
- PostgREST's `in.(...)` filter syntax breaks on a value containing a comma (e.g. the real list "Time to Lean, Time to Clean") — filter in JS after fetching instead of trying a DB `not in (...)`.
- **PostgREST silently caps any unlimited `.select()` at 1000 rows** — a bulk fetch across a growing table (not a small bounded catalog table like `items`) will quietly truncate once the table passes that size, with no error. Confirmed as a real, live bug in patch 41 for `inventory_counts` (velocity/par-suggestions/`last-per-item`) — par-suggestions was already silently dropping ~17 items and giving stale numbers for others before the fix. The fix: per-item targeted point queries (`fetchLatestCountAtOrBefore`/`fetchEarliestCountAtOrAfter`/`fetchFlowForItem` in `src/lib/usage-server.ts`, `runBatched` to cap concurrency at 15-20 at a time) instead of one bulk fetch across every item/row at once — a `.limit(1)` point query or a query scoped to one item's narrow window can never hit the cap. `src/lib/notes-server.ts`'s `fetchNotesWithJoins` instead pages the `notes` query itself (`.range()` loop) and scopes `note_replies`/`note_acknowledgments`/`note_photos` to just the note ids in scope. A **new call site reading `inventory_counts`, `order_history`/`order_history_items`, or `storage_moves` in bulk (no `.limit()`, no per-item scoping) risks the same silent truncation** — reuse the point-query helpers in `usage-server.ts` instead. Left alone deliberately (not bulk-fetch-truncated today, but not re-verified by patch 41): the Missed-tasks view (`/api/tasks?view=missed`, no date filter, growing unbounded — has an explicit `.limit(1000)` so it fails safe by capping rather than silently truncating, but has no "narrow your range" message) and the History view's 1000-row cap (date-range-scoped, 30-day default, same explicit-cap situation).
- `ZZTEST Shift Lead` is permanently `active = true` (see §2/§4) so it must be excluded by name wherever `shift_leads` is queried for `active = true` for real production behavior, not just test convenience — a new call site that forgets this will silently (and wrongly) count it. The three found and fixed so far: `src/app/api/pins/route.ts` GET (Change PIN screen's shift-lead list), `src/lib/notes-server.ts`'s `maybeAutoArchiveNote` (the ack-required-notes denominator), and `src/components/todo/NotesBoard.tsx`'s client-side fetch feeding the same denominator math live on the Notes board / History modal. `ZZTEST Owner` needs no equivalent filtering anywhere — owners are never queried by `active` for display/counting; every such list (`OWNER_NAMES` in `pins/route.ts`, `TASK_CREATORS` in `tasks.ts`) is a hardcoded name list, not DB-driven.
